# ガイド08: オントロジー設計ガイド(概念・用語と実践)

ガイド01〜05 が「COA という器を作る」手順だとすれば、本ガイドは「**器に何をどう入れるか**」、
つまりオントロジー設計の考え方を扱います。COA の本質はここにあります:
RAG のように文書を割って放り込むのではなく、**AI に使わせてよい知識の骨格(オントロジー)を
人間が設計・承認する**ことで、正確な集計・統制されたアクセス・文書知識の検索を両立させます。

本ガイドは、①COA の用語解説、②本リポジトリのサンプルデータ(変化点管理票)に
埋め込んだ設計判断のケーススタディ、③自分のドメインに適用するための設計手順、の3部構成です。
Web UI の操作手順そのものは [ガイド04](guide_04_knowledge_onboarding.md) を参照してください
(本ガイドは「その操作で何を判断すべきか」を扱います)。

---

## 1. なぜオントロジーか — RAG との違い

通常の RAG は「文書をチャンクに割って埋め込み、質問に似た断片を返す」仕組みです。
これは説明的な質問には有効ですが、次が苦手です:

- **集計・結合**: 「機種ごとの件数」のような質問に、断片の寄せ集めでは正確に答えられない
- **確定性**: 同じ質問に毎回同じ答えが返る保証がない(LLM の生成に依存)
- **統制**: 「誰にどのデータを見せてよいか」を断片単位で制御できない

COA は、データの**意味**(このカラムは何か、テーブル同士はどう関係するか、
この用語は何を指すか)を人間が承認したオントロジーとして持ち、質問を3層のカスケードで
解決します。集計は SQL で正確に、確定値はメトリクスで決定的に、文書知識はナレッジグラフ+
ベクター検索で返し、すべてに利用者ごとのアクセス制御が効きます。

設計者の仕事は「**どこまでを AI の推論に任せ、どこからを人間の承認済み知識にするか**」の
線引きです。以降の用語と手順は、すべてこの線引きのためにあります。

### 理論的背景: OBDA(Ontology-Based Data Access)

COA の構造化クエリは、OBDA という確立された研究分野の実装です。利用者(と LLM)は
物理テーブルではなく**概念層(オントロジー)に SPARQL で問い合わせ**、概念層と物理層を
つなぐ **R2RML マッピング**に基づいて、**Ontop**(OBDA の代表的 OSS 実装)が SPARQL を
SQL に変換します。COA の VKG コンテナは実際に Ontop を内蔵しており、変換だけを行って
実行はしない構成です(実装確認済み。実構築でも Playground の trace で
質問→SPARQL→SQL の変換過程を確認しています)。

従来、OBDA の導入障壁は「オントロジーと R2RML マッピングを何百テーブル分も手書きする
コスト」でした。**COA はこの両方を induction で自動生成し、人間の仕事を『書く』から
『承認する』に変えた**——これが COA の設計上の最大の価値です。本ガイドの設計手順が
「データの整形」と「レビュー・承認」に集中しているのはこのためです。

## 2. 用語集

### 2-1. 知識モデルの用語(オントロジーそのもの)

| 用語 | 意味 |
|---|---|
| **オントロジー (Ontology)** | ドメインの概念・関係・ルールを記述した形式知識モデル。COA は OWL/Turtle 形式で保存し、Neptune のナレッジグラフに実体化する |
| **クラス (Class)** | ドメインの「概念」。テーブル由来の induction では**1テーブル=1クラス**になる(例: `change_points`、`models`)。グラフ表示では**ノード**として描かれる |
| **属性/データタイププロパティ (Attribute / Datatype property)** | クラスが持つ値。**カラム由来**(例: `evaluation_result`、`change_date`)。proposal 画面では Attributes と表示される |
| **リレーションシップ/オブジェクトプロパティ (Relationship / Object property)** | クラス**間**の関係。**承認済み FK 由来**(例: change_points → models)。グラフ表示では**エッジ**として描かれる |
| **制約 (Constraint)** | カーディナリティ等のルール(例: 「各注文は必ず1顧客に属する」) |
| **ナレッジグラフ (Knowledge graph)** | ノードとエッジで知識を格納するデータベース(COA では Neptune)。オントロジーのクラス/プロパティに加え、**文書から抽出されたエンティティ**もノードとして格納される |
| **mapped クラス** | R2RML マッピングにより**実テーブルに裏付けられた**クラス。**Tier 2(構造化クエリ)で使えるのは mapped クラスのみ**。文書由来・基盤オントロジー由来のクラスは unmapped で、Tier 3 の検索・グラフ探索にのみ使われる |
| **VKG (Virtual Knowledge Graph) / Ontop / R2RML** | 概念モデル(オントロジー)と物理スキーマ(テーブル)の写像(OBDA の実装。1章の理論的背景を参照)。Tier 2 の第2経路では質問→SPARQL→(Ontop が R2RML で変換)→SQL と流れる。R2RML マッピングは induction から自動生成される |
| **基盤オントロジー (Foundational ontology)** | FIBO(金融)や Schema.org のような既存の参照オントロジー。カタログから読み込んで grounding の土台にできる |
| **Grounding** | induction で生成した新クラスを既存オントロジーの概念に**整列**させる仕組み(`rdfs:subClassOf` / `skos:*Match` を付与し、同じ概念の重複増殖を防ぐ)。モードは `NONE`(無効)/ `STANDARD`(名前完全一致のみ)/ `ENHANCED`(既定。LLM が意味の一致を検証) |

### 2-2. パイプラインと運用の用語

| 用語 | 意味 |
|---|---|
| **namespace** | 知識の独立した区画。データソース・オントロジー・メトリクス・権限がこの単位で束ねられる。ライフサイクルは ACTIVE → ARCHIVED → 削除の2段階 |
| **source(データソース)** | 知識の入力元。**Glue**(構造化=テーブル)と **Documents**(文書)の2種を今回使用 |
| **Scan** | ソースのメタデータを取り込む工程。発見(discovery)→ AI エンリッチ → 人間レビュー待ち(Pending review)と進む |
| **エンリッチメント (Enrichment)** | カラムに説明・同義語・タグを付与する工程。**DETERMINISTIC**(カラムコメント等の決定的情報。優先される)と **AI_INFERRED**(AI 推測)の2種のラベルが付く |
| **PK / FK 推論** | AI がテーブル間のキー関係を推測する(confidence 付き)。**人間の承認まで有効にならない** — ここが最重要の人間工程 |
| **Approve** | テーブル・カラム・キーを承認し、知識として採用する操作 |
| **Induction** | 承認済みソースからオントロジーを自動生成する工程(`Table to Ontology` 戦略)。LLM がスキーマを解析して proposal を作る |
| **Proposal** | induction の出力(オントロジー案)。Novel classes(新クラス数)、Proposal graph(ノード/エッジ図)、クラスごとの Relationships / Attributes を人間がレビューする |
| **Validate / HermiT** | proposal の論理整合性チェック。HermiT(OWL 推論器)が矛盾(CONSISTENT)・循環(NO_CYCLES)・連結性(CONNECTED)を検査する |
| **Accept** | proposal を承認し、namespace のオントロジーにマージ(発行)する操作 |
| **Explorer** | 発行済み知識の閲覧画面。Classes(クラス階層とグラフ表示)/ Ontologies(オントロジー一覧)/ Inducted sources の3タブ |
| **メトリクス (Metric)** | 名前付きの確定計算(完全な SELECT 文)。Name / Description / Expression / Dialect / Synonyms / Examples で定義し、Tier 1 の解決に使われる |
| **Tier 1 / 2 / 3** | 質問解決の3層カスケード(次章) |
| **tierOverride** | API / MCP で解決層を明示指定するパラメータ(1/2/3)。Playground UI には露出していない |
| **チャンク / 埋め込み** | 文書取り込みの単位。文書は分割(チャンク化)され、埋め込みモデルでベクター化されて OpenSearch に、抽出エンティティは Neptune に格納される |
| **Lexical Graph(文書ナレッジグラフ)** | 文書取り込みが構築するグラフの構造(graphrag-toolkit 由来)。文書 → **チャンク** → **トピック**(共通の話題)→ **ステートメント**(主語-述語-目的語の文)→ **エンティティ**の階層でグラフ化される。ベクター索引は **chunk と topic の2種**が既定(v0.1.0)で、Tier 3 の topic_beam 検索は topic 索引を起点にこのグラフを辿る — サンプルの Tier 3 検証でベクター検索(chunk 直接)と合成パス(topic 起点)の再現率が違ったのはこの構造による |
| **Document induction(文書からのオントロジー生成)** | テーブルだけでなく**文書からも**オントロジー案を生成できる。v0.1.0 の実装は LLM がクラス表・プロパティ表を直接抽出し、既存カタログと SKOS 整列させる方式。生成されたクラスは実テーブルに裏付けが無いため **unmapped**(Tier 3 専用)になる(※今回の構築では未実施) |
| **confidence / trace / Rationale** | 回答の確信度と実行過程。Playground の Rationale(歯車アイコン → Split panel から表示)でどの Tier がなぜ選ばれ、どんな SQL/SPARQL が実行されたかを確認できる |

## 3. 3層カスケードの役割分担(設計の出発点)

| | 発火条件 | 得意なこと | 設計者がやること |
|---|---|---|---|
| **Tier 1(メトリクス)** | 質問がメトリクス定義に一致 | 確定値を決定的に返す(LLM の SQL 生成なし・confidence 100%) | 頻出 KPI をメトリクス登録し、日本語同義語を付ける |
| **Tier 2(NL→SQL / SPARQL)** | mapped クラスのテーブルで答えられる質問 | 集計・結合・フィルタ(承認済み FK で JOIN) | スキーマ整備(コメント・統制語彙)と FK 承認 |
| **Tier 3(GraphRAG)** | Tier 2 で解決しない文書知識の質問 | 規程・ノウハウなど**表に無い知識**の検索と回答合成 | 文書の整備(粒度・ID・語彙) |

実測で判明している挙動(設計に効くもの):

- **Tier 1 は「その語だけ」の入力で発火する**(名前または同義語の一致。日本語同義語も有効)。
  語を文章に埋め込むと Tier 2 に落ちる(値は正しいが確定的実行ではなくなる)。
  複数メトリクスに曖昧一致した場合も Tier 1 は自らスキップする(公式ドキュメント)。
- **Tier 2 は「0行」も成功と扱う**。そのため表と文書に同じ内容を入れると、文書で答えるべき
  質問まで Tier 2 の空回答で止まり、Tier 3 に到達しない。→ **表に無い知識は文書だけに置く**のが
  設計の要点(4章の判断6)。
- **Tier 3 を確実に使うには** API / MCP の `tierOverride=3` または `rag_retrieval`(ベクター検索)を
  明示的に呼ぶ([ガイド05 ステップ5](guide_05_api_and_mcp.md))。

## 4. ケーススタディ: サンプルデータに埋め込んだ設計判断

本リポジトリの変化点管理票データセットは「COA 検証で問題なく使える」ように**逆算して設計**
されています。データを作った時点でオントロジー設計の大半は終わっている、という実例です。

### データとオントロジーの対応(実構築の結果)

```
テーブル                          オントロジー(induction の出力)
─────────────────────           ─────────────────────────────
change_points(100行・8列)  →   クラス change_points(Attributes 8)
models(10行・4列)          →   クラス models(Attributes 3+PK)
FK: model_name → models     →   オブジェクトプロパティ 1(クラス間のエッジ)
                                 HermiT 検証: 0 error(CONSISTENT・NO_CYCLES・CONNECTED)
文書 100件+規程1件          →   198+チャンク(ベクター)+抽出エンティティ(グラフ)
```

### 6つの設計判断

1. **マスタテーブルを分離した**(models)— 機種名を change_points に埋めるだけでも
   データは表現できますが、あえて機種マスタを分離しました。これにより FK 推論
   (`change_points.model_name → models.model_name`、confidence 92%)→ 人間承認 →
   オブジェクトプロパティ化、という COA の中核パイプラインが機能し、
   「スチームオーブンレンジの機種で起きた変化点は?」のような **JOIN 必須の質問**に
   Tier 2 が答えられるようになります(製品カテゴリは models 側にしか無い)。
2. **カラム名は英語+日本語コメント必須** — Glue/Athena の制約(日本語カラム名不可)への
   対応であると同時に、コメントが Scan 時に **DETERMINISTIC** エンリッチとして取り込まれ、
   AI 推測(AI_INFERRED)より優先されるため、Tier 2 の SQL 生成が安定します。
3. **評価結果を統制語彙にした**(`合格` / `条件付き合格` / `不合格(対策後合格)` の3値のみ)—
   自由記述にしないことで、`LIKE '不合格%'` のような**決定的なメトリクス式**が書け、
   規程文書(POLICY-001)側も同じ語彙で書かれているため、表と文書が用語で結びつきます。
4. **日付フィールドを持たせた**(変更日)— 「2024年に発生した不合格」のような
   時間軸の質問で Tier 2 の日付フィルタ生成を検証できるようにしました。
5. **全レコードに ID を振った**(CP-001〜CP-100)— 表の行と文書(1レコード=1文書)が
   ID で突き合わせられ、回答の引用・トレーサビリティが成立します。
6. **表に無い知識を文書だけに置いた**(POLICY-001: 評価結果ごとの事後対応ルール)—
   3章の実測のとおり、表と重複する知識は Tier 2 に吸収されます。Tier 3 の存在意義は
   「表に落ちない知識」にあるため、規程・ノウハウは**独立した文書として、表と重複させずに**
   投入します。

この設計の結果、FK の誤推論ゼロ・HermiT 検証エラーゼロ・3層すべての検証質問に正答、
という結果が得られました(詳細な検証結果: `docs/build-log/phase3.md` / `phase4.md`)。

## 5. 自分のドメインに適用する設計手順

新しいドメイン(実業務データ)を COA に載せるときの手順です。**1〜3がデータを触る前の
設計工程**で、ここに時間を使うほど後工程が楽になります。

### ステップ1: 質問インベントリを作る

利用者が実際に聞きそうな質問を10〜30個書き出し、各質問を3層に割り付けます:

- 毎回同じ答えであるべき確定値(件数・率・金額)→ **Tier 1 候補**(メトリクス化)
- 条件・集計・結合が変わる質問 → **Tier 2**(テーブルで答える)
- 「どうすべきか」「なぜか」等のルール・ノウハウ → **Tier 3**(文書で答える)

この割り付けが、テーブル設計・文書設計・メトリクス設計のすべての入力になります。

### ステップ2: 構造化データを整形する

- カラム名は英語、**日本語カラムコメントを必ず付ける**(判断2)
- 分類・状態を表す列は**統制語彙**にする(判断3)。表記ゆれは投入前に正規化する
- 参照関係は**マスタテーブルとして分離**し、FK 推論の対象にする(判断1)
- 時間軸の質問があるなら日付列を持たせる(判断4)
- 行に安定した ID を振る(判断5)

### ステップ3: 文書を整形する

- **1トピック=1文書**の粒度にする(巨大な混載文書はチャンク検索の精度を下げる)
- 文書に ID・対象(機種名等)のメタデータを見出しとして書き込む
- 規程・ノウハウは**表と重複させず**独立文書にする(判断6)
- 表側の統制語彙と**同じ用語**で書く(検索の一致率が上がる)

### ステップ4: Scan 結果をレビューする

Scan 後、各カラムのエンリッチ結果(説明・同義語・タグ)を確認します。
DETERMINISTIC(コメント由来)が正しく入っているか、AI_INFERRED の推測に誤りがないかを見て、
誤りは承認前に修正します。

### ステップ5: FK を検証して承認する(最重要)

- AI 推論の FK を**全件目視**する(どのカラム → どの参照先か、confidence)
- **実データで参照整合性を確認**してから承認する。誤った FK の承認は「エラーは出ないが
  JOIN 結果が NULL/欠落する」という最も気づきにくい不具合を生みます:

```bash
# 例: 子テーブルの参照値がすべて親に存在するか(0 なら整合)
QID=$(aws athena start-query-execution --region $COA_REGION \
  --query-string "SELECT count(*) FROM coa_testdata.change_points c LEFT JOIN coa_testdata.models m ON c.model_name = m.model_name WHERE m.model_name IS NULL" \
  --result-configuration OutputLocation=s3://$DATA_BUCKET/athena-results/ \
  --query QueryExecutionId --output text)
sleep 5
aws athena get-query-results --query-execution-id $QID --region $COA_REGION \
  --query 'ResultSet.Rows[1].Data[0].VarCharValue' --output text
```

### ステップ6: Induction の proposal をレビューする

チェック観点(操作は [ガイド04 ステップ7](guide_04_knowledge_onboarding.md)):

- Novel classes 数 = テーブル数と一致するか(初回・grounding なしの場合)
- Proposal graph のエッジ = 承認した FK と一致するか(余計な関係・欠けた関係がないか)
- 各クラスの Attributes 数 = カラム数と整合するか
- **Validate**(HermiT)が 0 error で通るか — エラーが出る場合は FK の循環や矛盾した制約を疑う

### ステップ7: メトリクスを設計する

ステップ1で Tier 1 に割り付けた質問をメトリクス化します:

- 選定基準: **頻出**・**確定値であるべき**・**監査で根拠を問われる**数値
- 命名: 英語名(`failed_count`)+**日本語の呼び名を Synonym に**(`不合格件数`)
- Expression は完全な SELECT 文・統制語彙前提の決定的な式にする(判断3が効く)
- 利用者には「メトリクスはその語だけを入力する」使い方を案内する(3章の実測)

### ステップ8: 質問インベントリで回帰検証する

Playground でステップ1の質問を順に投げ、**Rationale で「意図した Tier で解決されたか」**を
確認します。ズレの典型と対処:

| 症状 | 対処 |
|---|---|
| Tier 1 のはずが Tier 2 で解決 | 質問文がメトリクス名/同義語の単独入力になっているか確認。同義語を追加 |
| Tier 2 の JOIN が期待と違う | FK の承認漏れ・誤承認を確認(ステップ5) |
| 文書の知識に空回答が返る | 表と文書の知識が重複していないか確認(判断6)。文書知識は `rag_retrieval` / `tierOverride=3` の明示利用に寄せる |

## 6. 知識を育てる(運用と発展)

- **ソースの追加**: 完了済み文書ソースは Re-scan できないため、追加文書は別プレフィックスの
  新規ソースとして登録する(実測済み。[ガイド04](guide_04_knowledge_onboarding.md))
- **増分 induction と grounding**: 2回目以降の induction では、既存の承認済みオントロジーが
  自動的に grounding 対象になり、同じ概念の重複を防ぎながら知識を拡張できる
  (grounding モードは `ENHANCED` が既定。※初回構築は grounding なしで実施しており、
  増分 induction は**未検証**)
- **基盤オントロジーの利用**: FIBO 等をカタログから読み込み、自ドメインのクラスを
  業界標準概念に整列させられる(※未検証)
- **文書からの induction**: 規程・マニュアルなど文書しか無いドメインでは、文書から
  オントロジー案を生成する Document induction が使える(用語集参照)。生成クラスは
  unmapped(Tier 2 対象外)なので、構造化データ由来のオントロジーの**補完**と位置づける
  (※未検証)
- **proposal の手編集 / 既存オントロジーのアップロード**: Turtle 等の直接編集・持ち込みも
  可能(※未検証。手編集した場合は Validate のデータ型チェックに注意)

## 7. 検証水準

- **実測済み**: 3章の Tier 挙動、4章のケーススタディ全体(数値・検証結果)、5章の手順の骨格
  (実構築で同じ流れを2回実施)
- **公式ドキュメント+コード由来**: 用語集の定義(COA v0.1.0 の external-docs / 実装)、
  OBDA/R2RML/Ontop の構成、Lexical Graph の構造、grounding のモード仕様、
  mapped クラスの仕様、Tier 1 の曖昧一致スキップ
- **未検証**: 6章の増分 induction・基盤オントロジー・Document induction・手編集(該当箇所に明記)
