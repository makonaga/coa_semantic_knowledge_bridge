# ガイド06: アプリケーション統合(認証の設計)

構築したナレッジを本番アプリケーションやエージェントに組み込むときの認証設計です。
「Cognito はナレッジ開発用で、アプリからは認証なしで使う」という理解は誤りで、
**認証はナレッジ API の認可基盤そのもの**です。まず仕組みを理解してから、
形態別のパターンを選んでください。

## 認証・認可の仕組み(コードで確認済みの事実)

### 1. 認証なしで呼べる経路は存在しない

Context Manager / MCP サーバーの AgentCore Runtime には **JWT オーソライザが必須構成**として
組み込まれています(`serve-stack.ts` / `mcp-stack.ts`)。Bearer トークンのないリクエストは
エンドポイントの段階で 403 になります。トークンは OIDC の **ID トークン**で、
署名(JWKS)・`aud` クレーム・有効期限が検証されます。

### 2. 認証は「門番」ではなく「認可の入力」

Context Manager は毎回のクエリで JWT から `sub` / `email` / `groups` を抽出し、
**リクエストペイロードで自称した profile は信用しません**(`main.py` に明記)。
その検証済み識別子で DynamoDB の権限テーブルを引き、次を解決・強制します
(`role_resolver.py` + Cedar + SQL ファイアウォール):

| 制御 | 内容 |
|---|---|
| ロール | platform-admin / namespace-owner / data-analyst 等(アクション単位の Cedar 認可) |
| tableAllowlist | その利用者に**見せてよいテーブル**の限定 |
| columnDenylist | **隠す列**(PII 想定) |
| allowedMetrics | 実行を許すメトリクスの限定 |

> **v0.1.0 の注意**: 同一 namespace に複数のグラントを持つ利用者では、制限は**寛容側に
> マージ**されます(columnDenylist は全グラントが拒否した列のみ拒否)。無制限のグラントを
> 追加すると他グラントの列制限が実質無効になるため、グラント設計時に注意してください
> (上流の main ブランチでは deny 優先に強化済み)。

つまり「**誰が聞いているか**」でナレッジの見える範囲が変わります。これは通常の
RAG(Bedrock Knowledge Bases 等)には無い COA の中核価値であり、これを活かすには
アプリ側でもエンドユーザーの身元をトークンで伝える必要があります。

## 本番アプリでの認証パターン

### パターンA: エンドユーザーがいるアプリ(推奨)

ユーザーごとに IdP でログインさせ、その ID トークンで COA を呼びます。

- **トークンの有効期限は問題になりません**。MCP/CLI クライアントは
  ID トークン24時間・**リフレッシュトークン30日**(Web クライアントは1時間/12時間)。
  リフレッシュトークンによる自動更新は AWS SDK / Amplify が標準サポートしており、
  ユーザーは30日間パスワードを再入力しません。
- 本番では `USER_PASSWORD_AUTH`(env=dev のみ有効)ではなく **SRP / OAuth 認可コード+PKCE** を使います。
  MCP/CLI クライアントは PKCE + localhost リダイレクト構成済みで、IDE 系エージェント
  (Claude Desktop / Cursor 等)からの利用を想定しています。
- **社内 IdP のフェデレーション**: COA のオーソライザは OIDC 汎用設計
  (`allowedAudience` による `aud` 検証のみ。COA の infra/README に明記)のため、
  **Microsoft Entra ID / Okta 等の OIDC/SAML フェデレーション**を構成すれば、
  社員は普段の社内認証のままナレッジを使えます。IdP のグループクレームを
  `groups` にマッピングすれば、部署単位の列制限・namespace 制限も機能します。
  v0.1.0 の設定は SSM パラメータ `/coa/config` の COA 設定(`idpType` / `oidcSettings` /
  `claimsMappings`)で行います(COA の infra/README「IdP mode behavior」参照。
  ※本ガイドの実構築は Cognito 直接のみで、フェデレーションは未検証です)。

### パターンB: 人間が介在しないサービス/バッチ/エージェント

バックエンドに**機能アカウント(サービスユーザー)**を1つ作り、認証情報を
Secrets Manager に保管してリフレッシュトークンで回すのが、素の COA 構成で確実に動く形です。
サービスユーザーには必要最小限のロール(例: 対象 namespace の data-analyst)だけを
付与し、Admin グループには入れないでください。

> Cognito の `client_credentials`(M2M)方式も一般論としては存在しますが、COA の
> オーソライザは **ID トークンの `aud`** を検証する構成(アクセストークンの `aud` は別物)のため、
> 追加のクライアント設定と検証が必要です。採用する場合は事前に疎通確認をしてください。

### パターンC: 自前 API でラップ(全員同じ権限でよい場合)

アプリ → 自社 API(自前の認証)→ バックエンドが COA のトークンを管理、という構成です。
アプリから Cognito を完全に隠せますが、**全ユーザーが COA 上は同一プリンシパルになる**ため、
上記の行・列レベル認可を放棄することになります。全員に同じ範囲を見せてよいナレッジ
(全社共通 FAQ 等)なら合理的な選択です。

## パターン選択の目安

| 状況 | 推奨 |
|---|---|
| 社員向けアプリ・利用者ごとに見せる範囲を変えたい | **A**(IdP フェデレーション) |
| 夜間バッチ・Slack ボット・常駐エージェント | **B**(機能アカウント+Secrets Manager) |
| 公開範囲が全員同一・既存アプリに素早く足したい | **C**(自前 API ラップ) |

どのパターンでも、変わるのは「トークンの取り方」だけです。COA 側の API・MCP の
呼び出し方([ガイド05](guide_05_api_and_mcp.md))は共通です。
