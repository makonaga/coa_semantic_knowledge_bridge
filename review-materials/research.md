# AWS Context Ontology Accelerator (COA) 完全解説資料

## 1. COA（Context Ontology Accelerator）とは
COAは、組織が自社のビジネスに関する**オントロジー**（製品、顧客、ポリシー、運用ルールなどを機械可読にしたモデル）を構築・管理するためのAWSオープンソースアクセラレーターです。AIエージェントに対し、単なるデータではなく「業務上の意味（コンテキスト）」を渡すことで、正確で説明可能、かつ一貫性のある意思決定を可能にします。

## 2. 「社内の常識」をAIに教える仕組み（Scan → Model → Serve）

COAは以下の3つのステップを通じて、バラバラなデータに「意味の層」を付与します。

### ① Scan：データの収集と推論
*   **データ接続**: Glue Data Catalog、JDBC（PostgreSQL/MySQL/Redshift等）、S3、およびローカルアップロード（PDF/DOCX/TXT/MD）に対応しています。
*   **メタデータの補完**: AIがテーブルの列名から説明や別名を生成します。
*   **関係性の発見**: Glue等のデータカタログには存在しない「テーブル間の外部キー関係」をAIが推論します。検証では、6テーブル間の外部キーすべてをAIが正しく特定しました。

### ② Model：知識のモデル化と人間による承認
*   **オントロジーの自動生成**: スキャンしたデータから、概念（クラス）、関係（プロパティ）、ルールをOWL/Turtle形式で生成します。
*   **R2RMLマッピング**: 概念と物理テーブルの対応表（マッピング）を同時に作成します。これが「言葉」と「実際のデータ」を繋ぐ鍵となります。
*   **人間によるレビュー**: AIが生成した知識は「提案」として保存され、ドメイン専門家が内容を確認・修正・承認します。
*   **論理検証**: 承認前に**HermiT**などの推論器を用いて、論理的な矛盾がないか機械的にチェックします。

### ③ Serve：AIエージェントへの提供
*   承認された知識はナレッジグラフ（Amazon Neptune）に格納され、AIエージェントが**MCP（Model Context Protocol）**経由で参照できるようになります。

## 3. 回答を解決する3つの階層（Tier 1-3）

AIエージェントへの質問は、以下の3段階で解決が試みられます。

| 階層 | 名称 | 解決方法 | 特徴 |
| :--- | :--- | :--- | :--- |
| **Tier 1** | **定義済み指標** | 登録済みのメトリクス（例：売上の計算式）に直接マッチさせる | **決定的**な回答。AIの勝手な推測を排除し、組織で統一された数字を返します。 |
| **Tier 2** | **意味論的クエリ** | オントロジーを基にSPARQLまたはSQLを生成する | **VKG（Virtual Knowledge Graph）**技術（Ontop）を用い、概念的な問いを物理的なSQLに変換します。 |
| **Tier 3** | **グラフ/文書検索** | ナレッジグラフの探索や文書検索を組み合わせる | 文書を跨ぐ複雑な関係（マルチホップ）を探索。回答には必ず**引用元**が明示されます。 |

## 4. 技術アーキテクチャとインフラ構成

COAは16のCDKスタックで構成され、すべてのアセットはユーザーのAWSアカウント内にデプロイされます。

*   **Amazon Neptune**: RDF（オントロジー・スキーマ情報）とプロパティグラフ（文書から抽出された事実）の2つのモデルで知識を保持します。
*   **Amazon OpenSearch Serverless**: ベクトル検索を担当。検索用の`text`（別名や説明）と、プロンプト生成用の`context_text`（列の型や許容値）を分けて管理し、検索精度を高めています。
*   **Amazon Bedrock**: Claude 3.5 Sonnet（オントロジー生成・回答合成）やClaude 3 Haiku（メタデータ補完）などを用途別に使い分けます。
*   **VKG (Ontop)**: Fargate上で動作し、SPARQLを実データへのSQLに書き換えます。

## 5. RAGの補完および単独利用

*   **RAGの限界突破**: 従来のベクトル検索RAGが苦手とする「複数文書にまたがるルール確認」や「構造化データに基づいた正確な集計」を補完します。
*   **単独ナレッジとしての利用**: 一般的なRAGを構築しなくても、オントロジーのみをナレッジベースとして活用可能です。
*   **ガードレール**: `is_mapped`という仕組みにより、実データの裏付けがない概念に対してAIが勝手にSQLを書いて空振りするのを防ぎます。

## 6. 検証結果：なぜ「意味」を定義すべきか
ある検証では、同じ「売上」という質問に対し、以下の差が出ました。
*   **Tier 1（定義済み）**: 正しく「配送済み注文のみ」を集計。
*   **Tier 2（AIの推測）**: キャンセル分まで含めて集計してしまい、**金額に53%の差**が発生。
この結果は、AIに計算を「推測」させるのではなく、人間が承認した「定義」を使わせることの重要性を証明しています。

## 7. デプロイと導入の作業ステップ

1.  **環境準備**: Python 3.12, Node.js 22+, Docker, Java 17+, uv, pnpmをインストール。
2.  **インフラ構築**: GitHubリポジトリをクローンし、`make setup`の後に`make deploy-dev`を実行（約1.5時間）。
3.  **Namespace作成**: 部門やドメイン単位で独立した作業空間を作成。
4.  **Scan & Model**: データソースを接続し、AIが提案するメタデータやオントロジーを人間がレビュー・承認（数分〜数十分）。
5.  **Serve**: MCPサーバーを介して、AIエージェント（KiroやClaude Desktop等）から利用開始。

## 8. 留意点と前提条件
*   **レビュー体制**: 人間が内容を精査して承認するプロセスが必須です。確認なしに承認すると、誤った業務ルールが「正式な知識」として定着するリスクがあります。
*   **常時稼働リソース**: NeptuneやOpenSearch Serverlessなどのリソースを保持するため、コスト面での検討も必要です。
