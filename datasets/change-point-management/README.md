# 変化点管理票テストデータセット(電子レンジ)

COA 検証用の合成テストデータ。製造業における「機種ごとの変化点管理票」を模したデータ 100 件。

> **注意: 本データはすべて架空の合成データです。** 機種名は実在する Panasonic 電子レンジの
> 型番を識別子として借用していますが、変更内容・評価内容・評価結果はすべて創作であり、
> 実際の製品開発・品質情報とは一切関係ありません。検証目的以外に使用しないでください。

## ファイル

| ファイル | 用途 |
|---|---|
| `change_points.json` | 変化点管理票 100 件(パース後 JSON、COA ドキュメントソース/Tier 3 用の元データ) |
| `change_points.csv` | 同内容の CSV(UTF-8 BOM 付き)。Glue テーブル化して Tier 2(NL→SQL)検証に使用 |

## スキーマ

| フィールド | 説明 |
|---|---|
| `id` | 管理番号(CP-001〜CP-100)。引用・トレーサビリティ用に付与 |
| `機種名` | 対象機種(下記10機種) |
| `変更日` | 変化点の起票日(YYYY-MM-DD、2022〜2024年)。時間軸評価用 |
| `変更内容` | 変更の要約(1行) |
| `変更内容詳細` | 変更の背景・内容(2〜3文) |
| `評価内容` | 実施した評価の要約 |
| `評価内容詳細` | 評価方法・確認項目(2〜3文) |
| `評価結果` | 統制語彙: `合格`(89件) / `条件付き合格`(7件) / `不合格(対策後合格)`(4件) |

## 機種構成(10機種 × 各10件)

| 機種名 | 想定ポジション |
|---|---|
| NE-UBS10A | スチームオーブンレンジ(最上位) |
| NE-BS9A / NE-BS8A / NE-BS6A | スチームオーブンレンジ(上位〜中位) |
| NE-UBS5A | コンパクトスチームオーブンレンジ |
| NE-MS4A / NE-MS267 | オーブンレンジ(普及帯) |
| NE-FS3A / NE-FL1A / NE-FL222 | 単機能レンジ |

## 検証タスクとの対応(重要)

想定タスク: **新規機種開発時に、過去の変化点管理票から関連する変更内容と評価内容を提案する。**

検索・推薦の良し悪しを測れるよう、機種横断の「関連変更クラスタ」を意図的に埋め込んである。
評価質問を作る際はこのクラスタを正解セットとして使うこと。

| クラスタ | 内容 | 該当レコード |
|---|---|---|
| A: ドアパッキン EPDM 化 | 材質変更の横展開。低温環境で機種差あり | CP-011, CP-021(条件付き), CP-046(形状変更の亜種), CP-062 |
| B: マグネトロン EOL 対応 | 供給元変更の横展開。駆動方式で結果が分かれる | CP-031, CP-052, CP-061(条件付き), CP-071, CP-081(不合格→対策), CP-091(対策横展開で合格) |
| C: 赤外線センサー高分解能化 | 上位→下位への横展開 | CP-001, CP-012, CP-022 |
| D: 庫内セラミックコーティング | 生産ライン差分の確認が論点 | CP-003, CP-023, CP-051 |
| E: 電解コンデンサ複数購買化 | 差分評価方式の横展開。1件のみ定格不足 | CP-008, CP-018, CP-027, CP-036, CP-047(条件付き), CP-056, CP-065(不合格→対策), CP-075 |
| F: 自動あたためソフト改良 | センサー構成差による機種別調整 | CP-004, CP-014, CP-025, CP-054, CP-095 |
| G: スチームポンプ供給元変更 | 取付姿勢・配管長の機種差 | CP-002, CP-013(条件付き), CP-042 |
| H: 電源プラグ トラッキング対策 | 全社共通施策+差分評価 | CP-028, CP-037, CP-069, CP-089, CP-100 |
| I: 梱包パルプモールド化 | 物流ルート別の追加試験 | CP-009, CP-038, CP-058, CP-078, CP-088, CP-098 |
| J: ドアヒンジ・開閉耐久 | 異音・耐久対策の系譜 | CP-020(不合格→対策), CP-032, CP-067, CP-087, CP-097 |
| 安全系: ドアスイッチ変更 | インターロックの供給元変更横展開 | CP-074, CP-082, CP-093 |

## 時間軸の設計(時系列評価用)

`変更日` はランダムではなく、**クラスタ内の因果順序と矛盾しないように設計**してある
(`add_dates.py` が43個の順序制約を検証済み)。時系列の正解データとして使える構造は次の3種類。

1. **横展開の伝播順**: 上位機種で先行採用 → 下位機種へ展開。
   例: 赤外線センサー高分解能化は NE-UBS10A(2023-02)→ NE-BS9A(2023-06)→ NE-BS8A(2023-10)。
2. **不合格 → 対策 → 対策反映の系譜**: 対策済み評価は必ず不合格事例より後。
   例: マグネトロンEOLで NE-FL1A が不合格(2024-05)→ 対策反映済みの NE-FL222 評価(2024-08)。
3. **施策の波**: 全社施策(トラッキング対策プラグ: 2022-09〜2023-06)、EOL一斉対応
   (マグネトロン: 2024-01〜2024-08)、複数購買化(コンデンサ: 2024-04〜2024-11)のように、
   起点イベントから一定期間に集中する。

### 時系列評価質問の例

- 「ドアパッキンのEPDM化はどの機種から始まり、どの順で展開された?」
  → 期待: CP-011(2023-05)→ CP-021(2023-09、低温課題)→ CP-062(2024-02)の順序を日付付きで再構成。
- 「NE-FL222 のマグネトロン変更(CP-091)の前に、参考にすべき評価はあったか?」
  → 期待: 時間的に先行する CP-081(不合格→対策)を特定し「対策反映済み」の関係を説明(時間+因果のマルチホップ)。
- 「2024年に発生した不合格事例をすべて挙げよ」
  → 期待: CP-065, CP-081, CP-094 の3件(CP-020 は2022年なので含めない)。Tier 2 の日付フィルタ集計。
- 「電解コンデンサの複数購買化はいつからいつまでかかり、何機種に展開された?」
  → 期待: 2024-04〜2024-11、7機種8件(期間集計+件数)。

### 評価質問の例

- 「新機種でドアパッキンを EPDM に変更したい。過去の類似変更と評価項目、注意点は?」
  → 期待: クラスタ A を横断し、CP-021 の低温環境の条件付き合格に言及すること(マルチホップ+注意点抽出)。
- 「マグネトロンの供給元を変えるとき、非インバーター機で特に確認すべきことは?」
  → 期待: CP-061(モーディング)と CP-081→CP-091 の対策横展開の系譜を引用すること。
- 「評価結果が不合格になった変更は何件あり、どう対策された?」
  → 期待: CP-020, CP-065, CP-081, CP-094 の4件を列挙(Tier 2 の集計質問としても使える)。

## COA への載せ方(想定)

- **Tier 3(GraphRAG)検証**: JSON の各レコードを Markdown 等の文書に整形して LOCAL_UPLOAD / S3 ソースで登録。
- **Tier 2(NL→SQL)検証**: `change_points.csv` を S3 に置き、Glue テーブル(Athena からクエリ可能)として同一 namespace に登録。
- **Tier 1(メトリクス)検証**: 「不合格件数」「機種別変化点件数」などを完全な SELECT 文で登録。
